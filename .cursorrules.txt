# Глобальные правила разработки платформы ИИ-ботов (SaaS)

## Технологический стек
- Backend: Python 3.11+, FastAPI (асинхронный), SQLAlchemy 2.0 (async), Pydantic v2.
- Очереди и Кэш: Redis + Celery для асинхронных задач и вебхуков.
- Базы данных: PostgreSQL (основная реляционная), pgvector или ChromaDB (векторная для RAG).
- Frontend: Next.js 14+ (App Router), TypeScript, Tailwind CSS, React Flow (для холста конструктора).

## Правила для Backend (Python/FastAPI)
- Всегда используй асинхронность (`async def`) для эндпоинтов и работы с БД.
- Обязательно пиши Type Hinting для всех функций и методов.
- Для валидации входящих и исходящих данных всегда используй Pydantic v2 схемы.
- Разделяй логику: роуты (запросы) -> сервисы (бизнес-логика) -> репозитории (работа с БД).
- Обработка вебхуков от мессенджеров должна быть максимально быстрой: приняли вебхук -> сохранили в Redis/Celery -> отдали 200 OK. Никакой тяжелой логики внутри самого запроса.

## Правила для Frontend (Next.js/React Flow)
- Используй функциональные компоненты и хуки, избегай классовых компонентов.
- Для управления состоянием холста конструктора интегрируй React Flow в связке с Zustand или React Context.
- Все интерфейсы и типы данных должны быть строго описаны через TypeScript (избегай использования `any`).

## Обработка ошибок и логирование
- Вместо стандартного `print` всегда используй логирование (например, `loguru`).
- Каждая интеграция (Telegram, WhatsApp, CRM) должна иметь изолированный блок try-except с подробным логированием ошибок и структуры входящего вебхука.

## Правила для CRM-модуля
- Любая CRM-таблица обязана иметь `organization_id` и попадать под `base_crm_repository` — прямой `select()` по CRM-моделям в обход репозитория запрещён.
- Действия автоматизаций типа `send_webhook` обязаны проходить через shared SSRF-guard (allowlist схемы + блокировка приватных диапазонов) перед выполнением исходящего запроса.
- Название "Company"/"Организация" зарезервировано за tenant-моделью (`companies` / `organization_id`). CRM-сущность клиента компании называется исключительно `CrmAccount`.
- Все мутации сделок (`move_stage`, `assign`, `win`/`lose`) обязаны писать `TimelineEvent` — источник правды для истории сделки, а не подразумеваемая логика на фронтенде.
